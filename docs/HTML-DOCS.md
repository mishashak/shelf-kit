# 화면물 만들기

HTML 문서와 덱을 꽂이에 올릴 때 깨지지 않게 하는 규약입니다. 여기 적힌 것은 대부분
**로컬에서는 멀쩡한데 꽂이에서만 깨졌던 실제 사고**에서 나왔습니다.

문서 규약은 [CONVENTIONS](CONVENTIONS.md), 사용법은 [README](../README.md)에 있습니다.

---

## 1. 파일은 자기완결이어야 합니다

| 올리는 것 | 조건 |
|---|---|
| `.html` 하나 | 이미지와 CSS가 **전부 파일 안에** 있어야 합니다. 밖의 파일을 참조하면 서버가 거부합니다 |
| `.zip` | 이미지나 영상이 따로 있으면 이쪽입니다. **압축 루트에 `index.html`**이 오게 묶습니다 |
| `.md` | 회의록과 메모. 서버가 읽기용 화면으로 구워 줍니다 |
| `.pdf` | 원본을 그대로 보관하고 뷰어를 씌워 보여줍니다 |

zip을 만들 때 폴더째 묶으면 루트에 폴더가 하나 들어앉아 `index.html`을 못 찾습니다.
**폴더가 아니라 폴더 안 내용물**을 묶습니다.

```
PowerShell:  Compress-Archive -Path <폴더>\* -DestinationPath out.zip
```

## 2. 덱은 Reveal.js 구조로 짓습니다

HTML 덱은 `.reveal > .slides > section` 골격에 `Reveal.initialize(...)`로 초기화합니다.
슬라이드 한 장이 `<section>` 하나입니다.

**직접 만든 단일 캔버스 스캐폴드를 쓰지 않습니다.** `.slide.active`를 JS로 토글하며 한 장씩
보여주고 컨테이너에 `scale()`을 거는 식의 커스텀 구조를 말합니다. 이유는 하나입니다.
**그런 덱은 PDF로 내보낼 때 화면에 보이는 한 장만 인쇄됩니다.** Reveal은 `?print-pdf`로
전 슬라이드가 한 장에 한 페이지씩 자동 전개됩니다.

자유로운 픽셀 레이아웃이 필요하면 그 HTML을 `<section>` 안에 담으면 됩니다. Reveal을 버릴
이유가 아닙니다.

**올리기 전 자가검증**

```bash
grep -iE 'class="[^"]*reveal|Reveal\.initialize' 파일.html
```

안 걸리면 커스텀 이탈입니다. Reveal 골격으로 다시 감쌉니다. 꽂이도 업로드할 때 같은 점검을
걸어 비-Reveal이면 경고합니다.

## 3. 뷰어가 문서를 감싼다는 것을 전제로 만듭니다

⚠️ **꽂이는 원본 HTML을 그대로 서빙하지 않습니다.** 가공해서 iframe에 넣습니다.
그래서 문서 안에서만 성립하는 규칙이 깨집니다. 로컬 렌더로는 절대 안 잡히는 사고가 셋 있었습니다.

### `<base href>` 주입으로 문서 안 앵커가 404

번들의 상대참조를 풀려고 뷰어가 `<base href="...">`를 넣습니다. HTML 사양상 `#id` 프래그먼트는
**현재 URL이 아니라 base href 기준**으로 해석됩니다. 그래서 목차를 누르면 문서 밖으로 나가
404가 뜹니다. **고정 사이드바 목차를 쓰는 문서는 전부 해당됩니다.**

> 처방: 앵커 클릭을 가로채 `preventDefault()` 후 `scrollIntoView()`로 문서 안에서 처리합니다.
> base href가 있든 없든 똑같이 동작합니다.

### 자동 화면맞춤이 문서형을 덱으로 오인해 강제 확대

뷰어가 첫 `section`을 슬라이드로 착각해 창 크기에 맞추느라 1.15~1.30배로 확대하고, 창 크기마다
배율이 흔들립니다. 뷰어는 **조상에 transform이 걸려 있으면** 자체 맞춤 중으로 보고 손대지 않습니다.

> 처방: 본문 래퍼에 `transform: perspective(1000px)`을 겁니다(시각적으로는 아무 변화가 없습니다).
> `translateZ(0)`은 크롬이 단위행렬로 평탄화해서 판정을 통과하지 못합니다.

⚠️ **그 래퍼 안에 `position: fixed`를 넣지 않습니다.** transform이 걸린 조상은 fixed의 컨테이닝
블록이 되어, 고정 사이드바와 툴팁이 뷰포트가 아니라 래퍼 기준으로 붙습니다. 스크롤하면 사이드바가
같이 흘러갑니다. 래퍼는 본문(`<main>`)만 감싸고 `<nav>`와 툴팁 레이어는 바깥에 둡니다.

로컬에서 첫 화면은 멀쩡해 보여 눈으로는 안 잡힙니다. `scrollTo` 후
`getBoundingClientRect().top`이 0인지 **계산값으로** 확인합니다. `scroll-behavior: smooth`면
측정 전에 `scrollBehavior = 'auto'`로 꺼야 실측이 반영됩니다.

### 일반 규칙

**업로드형 플랫폼에 올릴 문서는 뷰어가 주입하는 것을 재현해 검증합니다.** 원본에 `<base>`와
뷰어 스크립트를 끼운 사본을 만들어 헤드리스로 돌리면 올리기 전에 잡힙니다.

## 4. 색과 강조는 극도로 절제합니다

⚠️ **색은 카테고리 분류가 아니라 주목 유도입니다.** 독자가 무엇에 집중해야 하는지 알게 하는 것이
목적이고, 전달력이 먼저입니다.

- 강조는 **구조(여백, 블록, 정렬)로 먼저** 합니다. 색과 굵기는 최후의 수단입니다.
- **의미색은 진짜 신호일 때 1~2곳만** 씁니다. 리스크에 빨강 한 점입니다. 다 칠하면 아무것도
  강조되지 않습니다.
- **카테고리마다 색을 칠하지 않습니다.** "강점은 초록, 약점은 빨강, A분류는 보라" 식으로 나누는
  것은 분류이지 강조가 아닙니다.
- 상태색은 **"지금 여기"를 알리는 데** 씁니다. 선택된 목차 항목처럼, 색이 독자의 현재 위치를
  알려주게 합니다.
- 브랜드 컬러 위에 의미색은 **얇은 레이어로만** 얹습니다. 채도 높은 색이 화면을 지배하면
  시선 강탈이 되어 전달력이 죽습니다.

같은 문구를 사이드바와 머리말과 본문에 중복 노출하지 않습니다. 행동 유도는 다 읽은 최하단에
한 번입니다. 상단과 중간에 남발하면 시선을 강탈합니다.

## 5. 폰에서 깨지는 곳

링크를 메신저로 보내면 **1차 소비 기기가 폰**입니다. 데스크톱에서 완성해 놓고 폰을 나중에 보면
늦습니다. 데스크톱 값을 그대로 내리면 깨지는 자리가 다섯 있습니다.

1. **여백을 다시 잡습니다.** 머리말 아래 여백과 첫 섹션 위 여백이 겹쳐 쌓여, 폰에서는 제목과
   첫 섹션 사이가 한 화면 가까이 벌어집니다. 모바일에서 패딩을 한 단계 내립니다.
2. **목차는 한 줄로 눕힙니다.** 세로 목차를 그대로 `flex-wrap`으로 깔면 항목 여섯 개가 세 줄이
   되어 제목보다 목차가 먼저 화면 절반을 먹습니다. `flex-wrap: nowrap` + `overflow-x: auto`로
   한 줄 칩 행을 만들고, 마지막 칩이 살짝 잘려 보이게 두어 밀 수 있음을 알립니다.
3. **중복 노출은 폰에서만 드러납니다.** 사이드바 푸터의 발행일과 머리말의 발행일은 데스크톱에서
   화면 양 끝에 떨어져 있어 안 걸리지만, 사이드바가 위로 올라오는 폰에서는 한 화면에 같이 뜹니다.
4. ⚠️ **그리드와 플렉스 칸의 기본 최소폭은 내용 크기입니다.** 한글에 `word-break: keep-all`을
   걸면 어절이 안 쪼개져서, 좁은 화면에서 칸이 줄어들지 못하고 화면 밖으로 밀려납니다. `1fr`을
   줬으니 알아서 줄 것이라는 기대가 틀리는 지점입니다. 값 칸에 `min-width: 0`을 눌러 줄바꿈을
   허용합니다. 항목명과 값 2열은 폰에서 아예 1열로 쌓는 편이 낫습니다.
5. **가로 방향 블록은 세로로 돌리면서 연결선도 같이 돌립니다.** 흐름 블록의 화살표를 좌우 기준으로만
   만들어 두면, 폰에서 칸은 세로로 쌓이는데 화살표만 옆을 가리켜 순서가 끊깁니다.

## 6. 검증

눈으로 봐야 아는 것은 렌더해서 보고, 고친 뒤에도 다시 봅니다. 몇 장만 확인하고 나머지를 미루면
안 본 곳에서 터집니다. 빈 곳과 휑함은 낱장이 아니라 전체를 훑어야 보입니다.

- **기기 에뮬레이션만으로는 부족합니다.** 크롬의 기기 모드는 엔진이 그대로 크롬입니다.
  화면물은 WebKit(사파리, 아이폰)으로도 한 번 봅니다. 빈 화면의 원인은 대개 요청 실패 로그에 남습니다.
- **PDF는 최종에만 만듭니다.** 반복 수정 중에는 HTML만 갱신하고, 확정된 뒤에 한 번 굽습니다.

## 7. 디자인 톤은 레퍼런스에서 시작합니다

색과 타이포를 즉흥으로 고르지 않습니다. **실제로 잘 만든 서비스의 디자인 토큰을 먼저 골라
선언하고** 그 위에서 만듭니다. 정해 두지 않으면 문서마다 톤이 흔들리고, 흔들리는 톤은 내용의
신뢰까지 깎습니다.

착수할 때 정하는 것은 셋입니다. **청중, 목적, 기조.** 이 셋이 다르면 같은 사실도 다르게 배치됩니다.
다 만든 뒤에는 바꿀 수 없으니 처음에 정합니다.
